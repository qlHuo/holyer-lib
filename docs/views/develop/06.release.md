# 发布流程规范

> **轻量级自动化发布：适用于个人/小团队 Vue 2 组件库**

## 一、为什么改造官方 Changesets 流程？

Changesets 官方推荐“PR 合并后发布”模式，适用于大型协作项目。但在 **个人或小团队场景** 下，该流程存在明显冗余：

| 官方流程 | 本项目方案 | 优势 |
|--------|----------|------|
| 1. `pnpm changeset`2. 自动创建 Release PR3. 人工审核 PR4. 合并 PR5. CI 触发发布 | 1. `pnpm changeset`2. `git commit && push`3. CI 直接发布 | ✅ **减少 3 步人工操作**✅ **发布延迟从小时级降至分钟级**✅ **适合高频小版本迭代** |

> 💡 **适用前提**：  
> - 代码已通过本地 lint/test 校验  
> - 提交者即维护者（无需多人审核）  
> - CI 环境具备完整构建与发布能力


## 二、整体架构与角色分工

本发布体系由 **开发者 + CI 工作流** 协同完成，职责明确：

| 角色 | 职责 | 关键动作 |
|------|------|--------|
| **开发者** | 触发版本变更 | 运行 `pnpm changeset` 并提交 `.changeset/*.md` |
| **Husky** | 本地守卫 | 阻止无 changeset 的 `packages/` 修改提交 |
| **GitHub Actions** | 自动化执行 | 检测 changeset → 升级版本 → 构建 → 推送 tag → 发布 npm |

### 协作流程
```plain
开发者修改 packages/ui/button
  → 运行 pnpm changeset（生成 .changeset/xxx.md）
  → git commit & push
    → CI 检测到 .changeset/*.md 存在
      → 执行 changeset version（更新 package.json + changelog）
      → 运行 pnpm build:all
      → 提交版本变更（--no-verify 跳过 Husky）
      → 推送 commit + git tags
      → 执行 changeset publish（发布到 npm）
```

> ✅ **核心价值**：  
> **“一次推送，自动发布”** —— 在保证安全的前提下最大化效率。


## 三、GitHub Actions 关键配置详解

### 1. 触发条件
```yaml
on:
  push:
    branches: [main]
    paths:
      - 'packages/**'       # 组件或工具包变更
      - 'package.json'      # 根依赖变更可能影响构建
      - 'pnpm-lock.*'
      - '.github/workflows/release.yml'
```

> ⚠️ **注意**：  
> 不监听 `docs/` 或 `example/`，避免文档更新误触发发布。


### 2. 核心发布步骤（全自动模式）

```yaml
- name: Publish packages
  if: steps.check_changesets.outputs.has_changesets == 'true'
  run: |
    pnpm exec changeset version          # 1. 生成 changelog + 升级版本
    pnpm run build:all                   # 2. 用新版本构建产物
    git add .                            # 3. 暂存变更（含 package.json / CHANGELOG.md）
    git commit --no-verify -m "chore(release): version packages"  # 4. 提交
    git push origin main --follow-tags   # 5. 推送 commit + tags
    pnpm exec changeset publish          # 6. 发布到 npm
  env:
    NODE_AUTH_TOKEN: ${{ secrets.NPM_TOKEN }}
    NPM_TOKEN: ${{ secrets.NPM_TOKEN }}
```

### 3. 为什么使用 `--no-verify`？

| 担忧 | 实际保障机制 | 结论 |
|------|--------------|------|
| “跳过 lint 会导致坏代码发布” | ✅ 本地 Husky 已校验代码质量✅ CI 在 `build:all` 中隐式运行 lint/test | **安全** |
| “CI 提交污染 Git 历史” | ✅ 提交内容仅为版本元数据（package.json / changelog）✅ 使用固定 bot 用户名 | **可接受** |
| “绕过 pre-commit 钩子” | ✅ 此提交由 CI 生成，非人为操作✅ 仅当存在 changeset 时才执行 | **合理** |

> 📌 **设计哲学**：  
> **“本地守门，CI 自动化”** —— 开发者负责质量，CI 负责机械操作。


## 四、安全保障机制

为防止意外发布，本流程设置三层防护：

| 风险 | 防御措施 | 验证方式 |
|------|----------|--------|
| **无 changeset 提交** | Husky 本地拦截 `packages/` 修改 | `git commit` 失败并提示 |
| **CI 工作区不干净** | 发布前检查 `git status --porcelain` | 若有未跟踪变更，CI 失败 |
| **NPM 发布权限过高** | `NPM_TOKEN` 仅授予 `@holyer-lib` 包写权限 | 最小权限原则 |

> ✅ **额外保障**：  
> - `concurrency` 锁定工作流，避免并发发布冲突  
> - `fetch-depth: 0` 确保 Changesets 正确计算版本  
> - 使用专用 `CI_GITHUB_TOKEN`（非个人 token）


## 五、总结

1. **本地必做**：
   ```bash
   pnpm changeset        # 生成版本日志
   pnpm lint && pnpm test # 确保代码质量
   git commit -m "feat(button): add loading state"
   git push
   ```

2. **禁止行为**：
   - ❌ 手动修改 `package.json` 版本号  
   - ❌ 直接向 `main` 推送无 changeset 的 `packages/` 变更  
   - ❌ 在 CI 中跳过 `build:all`

3. **监控发布**：
   - 查看 GitHub Actions 日志确认 `changeset publish` 成功  
   - 验证 npm 页面是否出现新版本  
   - 检查 `main` 分支是否新增 git tag（如 `v0.2.1`）

4. **未来扩展**：  
   - 若团队规模扩大，可随时切换回“PR 审核模式”，只需启用 `changesets/action` 即可，**无需重构流程**。
